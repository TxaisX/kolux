What was asked: the terminal pane menu (TerminalPane.tsx), the Explorer row menu (Explorer.tsx) and the status-bar menu
  (StatusBar.tsx) opened only on a right-click. Shift+F10 and the Menu key should open each one at the focused item, or at
  the element's own position when there is no item. The edit menu should move focus to its first row; Up/Down move, Enter
  picks, Escape closes and gives focus back to the field. Reuse the menu-key handling the other menus have; no second
  helper. +270 B or less on first load.

HOW THE ENGINE OPENS A MENU FROM THE KEYBOARD (probe: headless Edge over CDP, a page with a button, an input and a focusable
  list; Input.dispatchKeyEvent for Shift+F10 and the Menu key)
  - Both keys raise a native contextmenu event on the focused element, with button -1 (a mouse right-click has button 2)
    and clientX/clientY at the element's centre (an input: 4 px in from its left, at its vertical centre).
  - A keydown handler that calls preventDefault on F10 stops the Shift+F10 contextmenu. The Menu key still raises it (on
    Windows it acts on key-up).
  So every menu that already opens on contextmenu opens from the keyboard too, as long as nothing eats the key and the
  handler copes with where the event lands. No key handler was added: the engine's own path is the "existing handling",
  and button < 0 tells a keyboard menu from a mouse one where that matters.

FIXED
  - Terminal pane menu. The terminal's key handler encoded Shift+F10 (and the Menu key) for the program in the pane and
    called preventDefault, so the engine raised no contextmenu. src/terminal/PaneMenu.tsx: menuKey(e) names the two keys;
    TerminalPane.tsx: the custom key handler returns false for them before anything else, so the terminal leaves them to
    the engine. rightClick: a contextmenu with button < 0 always opens the pane menu at the event's point (the focused
    terminal's centre), whatever the right-click paste and mouse-tracking settings say; those settings are about the mouse.
    The link-menu guard (TERM-094), which drops the contextmenu after a right-click on a hovered link, lets a keyboard
    contextmenu through, since no link menu opened for it.
  - Explorer row menu. Focus sits on the tree itself (role=tree, aria-activedescendant names the active row), so the
    engine raises contextmenu on the tree, not on a row, and nothing listened there. Explorer.tsx: the tree's
    onContextMenu (keyContext) takes a keyboard contextmenu (button < 0, raised on the tree itself) and opens the active
    row's menu just under that row (16 px in from its left edge), or at the engine's point when the row is scrolled out
    of the drawn rows. A mouse right-click on blank list still opens nothing. The row-is-a-folder test the rows used
    inline moved to dirRow() so both paths share it.
  - Edit menu. src/editmenu/EditMenuHost.tsx: the menu used its own window listener for Escape only and left focus in
    the field. It now uses useMenuFocus (src/chrome/dialogFocus.ts), the helper the status-bar, New tab and More tabs
    menus use: focus on the first enabled row, Up/Down/Home/End move (wrapping), Tab closes, Escape closes, and focus
    goes back to the field. Enter on a row is the button's own click, which runs the edit on the field (runEdit puts
    focus back on the field first, so the field's selection is what Cut/Copy act on).

NOT REPRODUCED
