Findings fixed (review of 426ff7d6):
  P1-A  CLI `orchestration.worker-start` with --name never called note_foreign_base: a fork
        branch checked out through it was pre-trusted.
  P1-B  name-based detection (`rev-parse --symbolic-full-name <base>` + the branch's upstream)
        missed a local branch tracking the fork, a bare sha, `fork/theirs~0` and any other rev
        expression that resolves to a stranger's commit.
  P2    from_foreign_remote treated any git error as "not foreign" (fail-open).
  P3    the plain record was written first and the marker added in a second write, so a crash
        or a concurrent reader between the two saw a clean record; git ran under the store lock.
  P3    workspace_from_item's issue path never marked at all.

Design (content-based, fail-safe, one write):
  projects::head_is_on_origin(dir) -> bool    (projects.rs ~312)
      `git rev-parse --verify HEAD^{commit}` then
      `git for-each-ref --contains <sha> --format=%(refname) refs/remotes/origin/`,
      both through crate::git::run_within with READ_TIMEOUT (30 s). True only when at least one
      `refs/remotes/origin/<name>` line comes back. A git error, a timeout, a malformed sha, no
      `origin` remote, an empty listing: all false. It is called in the git-only creation layer
      (create_workspace_until, open_branch_workspace_until), inside repo_turn, with no store lock
      held (T-442-b kept).
  Created.own: bool  (#[serde(skip)], never sent to the window)
      set from head_is_on_origin by the two creation functions above; pr_checkout::open sets it
      false by construction (a pull request's head is never Kolux's own).
  projects::record_made(store, project, made, origin)    (projects.rs ~328)
      the single writer of a fresh madeBy record. When !made.own it puts `"prEver": true` into the
      record BEFORE the one set_origin call, then note_seen. There is no window with a clean
      record on disk.
  projects::note_seen no longer writes `{madeBy:"app"}`; it only maintains the seen list. A
      caller that wants a record goes through record_made and so through the own check.
  projects::set_origin carries an existing `prEver: true` over onto any rewritten object record
      (belt for save_details, the CLI issue/comment edit and any future writer).
  from_foreign_remote and note_foreign_base deleted.
  create_named / create_named_until gained `origin: Option<serde_json::Value>` so the caller's
      record (CLI madeBy "cli" with parent/cwd/issue, the app's issue link) is the first and only
      write. open_named_until added for the open-branch path (same shape).

Every creation path and how it decides the marker:
  workspace_create (window, blank or with issue)        -> create_named_until -> record_made(own)
  workspace_from_item (window, from an issue)           -> create_named           -> record_made(own)
  workspace_open_branch (window, existing branch)       -> open_named_until       -> record_made(own)
  workspace_create_fresh (window)                       -> create_fresh_from -> create_fresh_workspace -> record_made(own)
  CLI worktree.create (with or without --base-branch)   -> create_named(origin=cli record) -> record_made(own)
  CLI orchestration.worker-start --name [--base-branch] -> create_named          -> record_made(own)
  CLI orchestration.worker-start (no --name)            -> create_fresh -> create_fresh_from -> record_made(own)
  hooks.rs test helper                                  -> create_fresh_from     -> record_made(own)
  workspace_open_pr (window, pull request)              -> pr_checkout::open (own=false) then its
                                                           own set_origin with `prEver: true` (unchanged, already correct)
  Remaining set_origin callers (save_details, CLI issue/comment edit, forget_origin) rewrite or
  remove existing records; set_origin keeps the marker on a rewrite. No path writes a fresh madeBy
  record without going through record_made.

Accepted costs (frozen by the coordinator, 2026-11-09):
  - A repo whose canonical remote is not named `origin` never gets pre-trust: its worktrees are all
    marked prEver and Claude/Codex ask their own "trust this folder?" question. Correct, just slower.
  - A worktree started from unpushed local commits (HEAD not reachable from any origin/* ref) is
    not pre-trusted either, even though the commits are the user's own. Same effect: the agent asks.
  - Any git failure or timeout during the check costs pre-trust, never grants it.
  - The CLI test fixture had to gain a bare `origin` remote so its own-branch cases stay pre-trusted.
