PART 1 - CONFIRMED FIRST (chat-sessions.md:11 was marked UNSURE)
- Real. session_delete (src-tauri/src/session_files.rs) located the transcript and removed it with nothing asking
  whether a pane was running that session. The window side (sessions/SessionFiles.tsx -> files.ts -> invoke
  "session_delete") asks "are you sure" and names the session (that half of F4 was already done), but checks no pane.
  The resume block (resume.ts) only looks at turns. So the files of a session an agent was still writing could go.

THE FIX
- status.rs: transcript_live(file, folder) - true when an open pane's hooks last reported `file` as their transcript,
  or a file inside `folder` (the session's own folder: a sub-agent's hook names its own transcript there). The
  records it reads are the ones terminal_ended removes, so only open panes count; a pane that starts a new chat names
  its new transcript, so its old one becomes deletable. Both paths are resolved by the filesystem (canonicalize), so
  case and / against \ never hide a match; they are resolved after the sessions lock is let go.
- session_files.rs delete(): after locate, a live transcript is refused with "This session is still open in a pane. Close
  that pane, then delete the session." and nothing is removed. The window shows a refused delete's reason in its note
  line; sessions/SessionFiles.tsx now also hands focus back to Delete… after a refusal.
- Refuse, not warn: the delete is permanent and the agent would keep writing to the file it lost.
- Fails safe: a shell pane where the agent was quit (/exit) keeps its last transcript until the pane closes, so the
  delete is refused until then (the message says to close the pane).
- Not seen: a pane whose agent has no hooks or has not reported yet. Its session can still be deleted behind the
  window's own question (after-list).
