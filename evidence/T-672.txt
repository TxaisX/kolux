T-672 - The Skills page from the keyboard, and honest about failures (DT-C108; UX audit findings/skills-automations.md:5, :6, :7, :15, :16, :19 and :22, findings/keyboard.md:9 (the SkillUpdate part) and findings/backend-wiring.md:7)
Worker 2f, branch s-2f/ux-3, base e93a23ba (uncommitted at the time of writing), 2026-11-02.

WHAT CHANGED
- The Update Kolux skills dialog takes the keyboard when it opens (focus lands on Close), Escape
  closes only that dialog, Tab wraps inside it, and focus goes back to where it was when it closes.
  When focus falls to nothing while it is open (Stop leaves, or the button just pressed turns off),
  the dialog box takes it back on that render, so its Escape and Tab keep working and Tab does not
  walk into the page behind. Focus goes back to the button that opened it; when that was Review (which
  is replaced while the dialog is open) it goes to the new Review button, and when the opener is gone
  to the page's More actions button or the Skills heading, never to a terminal hidden behind the page.
  Asking for Install while the dialog is already open moves focus to the Install panel and leaves
  nothing pending for the next open.
- The Skills page's own Escape does nothing while any dialog is showing: the Update dialog, a skill's
  details, the Delete confirmation, its result or its error (the page counts its own dialogs, because
  the shared overlay scan does not list the alert dialogs), whatever has focus. A focus that falls
  to nothing is now caught by the Update dialog (above); when the last menu or dialog of the page
  closes with focus on nothing, and the button that opened it is gone (a deleted row), focus goes to
  the Skills heading so the next Escape does not close the page.
- A skill update whose progress cannot be read is tried again; the third failure in a row ends the
  run as failed: the status bar says "Skill update failed" and the dialog gives the reason, instead
  of "Updating N skills" for ever. A read that fails and is followed by a good one starts the count
  again. Starting an update while a progress read is in flight leaves one poll chain: a read of the
  old chain that comes back late is ignored.
- A refused Stop shows its reason in the dialog.
- Delete skills is switched off, with the reason, while the scan failed; a selection in progress
  ends when a rescan fails.
- More actions has "Install / reinstall Kolux skills" (first entry). It opens the existing Update
  dialog on its Install panel and puts focus on the panel. It is off, with the reason, when the scan
  found no Kolux skills. No new back-end command.
- The "Type in terminal" button is gone from the Install panel, with the unused prop. The Skills
  page has no way to reach the active terminal, so the button could never appear. Copy command stays.
  To bring it back, the window that shows the page (shell/window/Content.tsx) would hand it a typer.
- The More actions, Filter by agent and row action menus put focus on their first enabled item when
  they open, step with the arrow keys (wrapping; Home and End jump), and give focus back to their
  button when they close. The More actions button now has the name "More actions".
- Not touched: anything under automations (the other half of row 19), tasks, board, inbox, and
  the chrome/projects/shell row (skills-automations.md:17).

WHY
Static UX audit lane B, the Skills half (findings/skills-automations.md, keyboard.md:9,
backend-wiring.md:7): the Update dialog never took the keyboard, so Escape closed the whole Skills
page behind it; a skill update whose progress read failed spun for ever; a refused Stop was dropped;
Delete skills stayed on after a failed scan; Install / reinstall was reachable only inside a dialog
that has nothing to do when every skill is current; and a "Type in terminal" button could never be
drawn. DT-C108 records it; it reverses SKILL-028's "Install opens a terminal with the command typed"
for the Skills page's Install panel.
