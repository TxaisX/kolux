T-671 - The Automations page: errors, Escape, Run now twice, and a way to every control (DT-C107; UX audit)
Worker 2f, branch s-2f/ux-2, base e93a23ba (uncommitted at the time of writing), 2026-11-02.

WHAT CHANGED
- Run now twice: the button (row menu and opened page) is disabled and reads Starting while the ask
  is on its way. Kolux itself refuses a manual run of an automation that still has a run pending,
  dispatching or dispatched, with a message naming the run in progress. The check and the new run
  share one lock. Timetable, event and catch-up runs are not refused. Running by hand from the
  command line (automations.run in automations_cli.rs) goes through the same run_manual, so it is
  refused the same way.
  A dispatched run holds Run now only while it has a terminal, or for 120 seconds (SETTLE_MS) after
  it was dispatched. A new-pane run gets its terminal only when the window starts the pane; if the
  window never does, the run would stay dispatched until the next restart, so after the 120 seconds
  it no longer blocks. A young one without a terminal is refused with "NAME is still starting
  (run #N); try again in a moment". A run with no dispatch time counts as old.
- The opened automation page now shows the last action's note and the delete confirmation (they
  were drawn only on the list), and has Edit and Delete in its header.
- The row menu has a backdrop: a click outside, or Escape from anywhere, shuts it.
- Escape on the Runs dashboard goes back to Automations; on a run page it goes back to Runs. It does
  nothing over a dialog, a menu or a text field.
- A failed runs read shows "The runs could not be read" with the reason and Retry, not "No runs
  yet" and zero counts. Run rows hold a button that opens the run, so the keyboard reaches them.
- Refresh keeps the rows already shown when the read fails and says so in a note. A failure of the
  Hermes and OpenClaw refresh is shown in the same note instead of being thrown away.
- With no projects, the bar and the empty state offer Add a project, which opens the sidebar's
  existing Add Project dialog.
- Templates are hidden when editing a saved automation.
- A worktree list that cannot be read shows the real reason with Try again; Save's hint says to use it.
- Closing the dialog (Escape, Cancel, the dark area) asks "Discard your changes?" when any field the
  form submits differs from how the dialog opened (name, prompt, agent, project, worktree, base
  branch, setup, session reuse, catch-up, precheck, timetable, time zone, trigger, Hermes folder).
  The dark area closes it only when the press and the release both landed on the dark area.
- Refresh shows a failed Hermes and OpenClaw ask and a failed list read together in one note.
- Deleting a Hermes or OpenClaw job says it is removed from that tool and that Kolux keeps no
  history for it; Kolux automations say their run history goes with them.
- The Automations bar has a Close button; the Refresh button is disabled and marked busy while it runs.
- Run now's hold on the page is one helper (holdWhile in automations/model.ts): the automation's id
  is held while the ask is on its way and let go when it returns, on success and on failure; it
  covers Kolux automations and Hermes and OpenClaw jobs.
- One line outside the lane's usual files: src-tauri/src/automations_cli.rs calls
  automations::run_manual instead of automations::run(.., "manual") for automations.run, so the
  command line gets the same refusal. Flagged in the PR.

WHY
Static UX audit lane B, the Automations half (findings/skills-automations.md, stress.md:9,
empty-error.md:11 and :12, backend-wiring.md:10): Run now could start the same automation twice
(two agents in one worktree) from the button, the row menu and the command line; the opened
automation page showed no note, no delete confirmation and had no Edit or Delete; the row menu had
no way out; Escape did nothing in Runs; a failed runs read said "No runs yet"; a failed refresh
replaced the rows with an error; the dialog threw away unsaved work on Escape, Cancel or a stray
drag on the dark area; Templates overwrote a saved automation; with no projects the page offered
nothing. DT-C107 records it. The 120-second limit is there because a new-pane run gets its
terminal only when the window starts the pane; without it one lost pane would block Run now until
the next restart (the Opus review's one BLOCKING item).

REVIEW
Opus review B+ (1 BLOCKING: a stale dispatched run blocked Run now for ever; plus smaller items)
-> fix pass (the 120-second limit, the scrim press-and-release rule, the unsaved check over all
fields, joined refresh notes, the in-flight hold) -> Opus re-review A- with two
SHOULD-FIX items, both fixed after it: (S1) after a restart a run still waiting for its pane
(settleBy set) now holds Run now until settleBy, however old its dispatch, so a resumed run is
not started twice; (S2) when Run now starts, this automation's old runs whose pane never started
are closed as failed ("This run's terminal never started"), so the new run's pane is credited to
the new run and not to the older orphan. Follow-ups (not in this PR): S3 Add a project does
nothing with the sidebar collapsed (needs Content.tsx, outside this lane); N1 a red refresh note
can stay after a later good refresh; N2 rows 2-4 are tested through helpers only; N3 Keep editing
moves focus to the prompt box; N4 a clock stepped back can hold the guard longer.
-> fresh Opus review (opus-high-review) of the S1/S2 change and its two tests only: A-. S1 holds
with no gap against the settle step's own deadline; S2 closes only runs that no longer hold Run
now, all under one store lock, and leaves scheduled and event runs alone; removing either fix
makes its test fail. Its one SHOULD-FIX is older than this PR and outside Run now: a scheduled
or event run, or a run of another automation in the same worktree, can still have its pane
claimed by an older run whose pane never started, because claim takes the oldest free run. The
suggested follow-up moves the stale-run close into the 30-second settle step and makes claim
skip stale runs, so every trigger is covered. Its nits (N1 detail wording for a run past
settleBy, N2 the start event sent before the run is marked dispatched, N3 more guard rows in the
store test) go with that follow-up. No code changed after this review.
