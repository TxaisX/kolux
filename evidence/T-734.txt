T-734 - Cancel a running download, Show a finished one in its folder (DT-C170; UX audit W3 queue refill 3, backlog-sweep-49 #15)
Worker 2f, coordinator 57, branch s-2f/t734 from main 99b4a9d2 (main b2b6cd7f merged), 2026-11-03. Cap +300 B.

BEFORE
- The download strip in a browser tab (BROW-013) showed progress for a running download, with no way to
  stop it short of closing the tab. A finished row offered Open only, not the folder it landed in.
- Each new download of a tab dropped that tab's ended rows from the registry, so a row the strip still
  showed could be unknown to the app.

AFTER
- A running row has Cancel. It calls browser_download_cancel with the row's key: the app finds that tab's
  running WebView2 download by its file (the engine's DownloadStarting event now keeps each running
  operation for its tab) and calls its Cancel, which stops it. The row reads
  cancelled. A download that ended in the meantime is refused with "the download already ended"; a row that
  is not running gets "the download is not running". Errors show in the pane's note line.
- A finished row has Show in folder beside Open. It calls browser_download_reveal with the row's key; the
  file manager opens with that file selected (the same reveal the app uses elsewhere). An unknown key says
  "that download is no longer known; open the Downloads folder".
- Cancel and Show in folder share one button slot, so a row shows at most one of them. Failed and cancelled
  rows show neither.
- The registry keeps up to 64 rows across tabs; past that the oldest ended rows go first and a running one
  never does.
- Both names are literal invoke calls registered in lib.rs, so scripts/invoke-contract.mjs checks them: OK.
- Not on Windows, Cancel answers "cancelling a download needs WebView2 (Windows)".
