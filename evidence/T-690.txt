T-690 - An automation run's pane is credited to the run it was opened for (DT-C126)
Worker 2f, branch s-2f/claim, stacked on s-2f/ux-2 (#115, T-671) at 7f4831d8, 2026-11-03.
Merge after #115.

WHAT CHANGED
- The start notice already carried the run's id. The window now hands it to the pane it opens for
  that run, as KOLUX_RUN_ID in the pane's environment (src/projects/startArgs.ts sessionEnv,
  startTail, startFields; src/launch/launchActions.ts startIn and openIn). A KOLUX_RUN_ID the agent's
  own settings hold is dropped on that path, and the window's own value goes last.
- The runtime reads that value before the environment is handed to the new process
  (automations::run_in, called in terminal.rs next to the dispatch id) and gives it to claim.
- claim (src-tauri/src/automations.rs) now:
  - pane that names a run Kolux knows: credited to that run only, while it is pending, dispatching
    or dispatched with no pane yet, of the same agent and worktree. A run already followed, a
    finished run, or one in another worktree takes nothing, and there is no fallback to another run.
    A run still pending when its pane starts (the start notice goes out before the run is marked
    dispatched) is credited too, and keeps its pane through the dispatched update.
  - pane that names no run Kolux knows (one reopened after a restart, whose environment is not
    saved, or one whose id came from the agent's settings): credited only to a dispatched run that
    is inside its settling period after a restart, had a pane before it, and, when its old hook
    pane is known, only on that same hook pane. The oldest such run wins.
  - so a tab the user opens is never credited to a run, and a run whose pane never started (a
    scheduled or event run, or another automation's run in the same worktree) never takes anyone's
    pane, before or after a restart.
- Existing tests now claim a fresh run's pane the way the window does, with the run's id; the two
  restart tests reopen on the run's own hook pane. tests/cards_09.rs gets the same change.

WHY
The T-671 re-review (#115) left one SHOULD-FIX older than that PR: claim credited a new agent pane
to the oldest pane-less dispatched run of that agent in that worktree. An older run whose pane never
started, from a schedule, an event or another automation in the same worktree, took the new run's
pane, so the new run was never followed and never finished, and the old one was credited with work
it never asked for. #115 closed only Run now's own orphans. 57's brief: fix the root cause in the
claim itself, match the claim to the run it belongs to, and keep the orphan from winning.

FOLLOW-UPS (not in this PR)
- A scheduled or event run whose pane never started now harms nothing, but it still reads
  dispatched until the next restart, when settling closes it. Closing it in the 30-second settle
  step is a separate change.
- The window wiring of the run id (useCliBridge to startIn to openIn) is tested through
  startTail/startFields only; a swap of the dispatch and run arguments would still type-check.
- Run ids are numbered one past the highest kept run, so an id can be given again after old runs
  are pruned; a pane still naming the old id then names the new run. Ids that are never reused
  would close this.
- Pane keys handed out after a restart can repeat a key a run remembers from before it, so a
  different pane could be taken as that run's hook pane while it settles. Keys that never repeat
  across restarts would close this.
