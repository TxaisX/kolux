  Finding 1: core.fsmonitor=false alone left a repository's own filter.<x>.clean running on
  `status --porcelain=v2` and `diff --numstat -z` (stale index stat, as in a zip-extracted folder),
  and diff.<x>.textconv on `show`/`diff` of a commit.
  Fix (git.rs): git::command lists `git config -z --show-scope --get-regexp
  '^filter\..*\.(clean|smudge|process|required)$|^diff\..*\.(textconv|command)$'` for the folder and
  blanks every key in the local/worktree scope through further GIT_CONFIG_KEY_n/VALUE_n slots
  ("" for the programs, "false" for required, so a blanked clean filter does not fail the read).
  git-lfs's own three standard lines are the one exception (a repository with `git lfs install
  --local` keeps working). The listing is cached per folder while .git/config and config.worktree
  (mtime + size) are unchanged, so a status read costs the same git processes as before (T-033-e).
